# Security Steering File

## Overview

This file defines the security standards, controls, and requirements that apply to every project in the AI-10 Portfolio. Security is not optional and is not deferred to a later phase. Every ticket must consider its security impact. The security gate must be passed before any release.

---

## 1. Authentication

**Rules:**
- All non-public endpoints require authentication
- Support API key authentication for machine-to-machine and JWT/OAuth2 for user-facing interfaces
- Tokens are short-lived; refresh token rotation is implemented where applicable
- Authentication failures return 401 with a generic message; do not reveal whether the user exists
- Brute-force protection is applied to authentication endpoints (rate limiting + lockout)
- Local development auth is documented; never commit real credentials to the repository
- Authentication is implemented once in middleware; never replicated per-endpoint

**Implementation pattern:**
```
middleware/auth.py → extracts and validates token → attaches identity to request context
domain operations check identity from context, never from raw headers
```

---

## 2. Authorization

**Rules:**
- Authorization is enforced at the domain layer, not only at the API routing layer
- Every domain operation explicitly checks whether the requesting identity has permission to perform it
- Default-deny: if a permission check is missing, access is denied
- Authorization decisions are logged for auditing
- Cross-tenant data access is impossible by architecture (tenant ID is part of every query, not just a filter)
- AI-generated actions that have external side effects require explicit user authorization before execution

---

## 3. Role-Based Access Control (RBAC)

**Standard roles per project:**
- `admin` — full system access including configuration and user management
- `member` / `operator` — can use core features but cannot manage system configuration
- `viewer` / `readonly` — read-only access to non-sensitive data
- `service` — machine-to-machine API key access with scoped permissions

**Rules:**
- Roles are defined in code and configuration, not hard-coded per-user
- Role assignments are stored in the database and auditable
- Least-privilege: assign the minimum role required for a task
- Role escalation requires explicit human approval
- Service accounts use API keys, not user credentials

---

## 4. Secrets Management

**Rules:**
- No secrets, API keys, passwords, tokens, or credentials in source code
- No secrets in configuration files committed to version control
- Use environment variables for all secrets in local and CI environments
- Use a secrets manager (AWS Secrets Manager, HashiCorp Vault, or equivalent) for production
- `.env.example` shows all required keys with placeholder values; `.env` is always in `.gitignore`
- Secret rotation is documented and tested
- Secrets must not appear in logs, error messages, or API responses
- CI/CD secrets are stored in the CI platform's secret store, never in workflow files

**Pre-commit check:**
- A pre-commit hook or CI step scans for common secret patterns (using `detect-secrets` or `trufflehog`)

---

## 5. Data Protection

**Rules:**
- Classify all data at design time: Public / Internal / Confidential / Restricted
- Confidential and Restricted data is encrypted at rest
- All data in transit uses TLS 1.2+ (TLS 1.3 preferred)
- Database backups are encrypted
- Data retention periods are defined per data type and enforced programmatically
- Data deletion requests are handled within the defined SLA
- Test data does not contain production personal data

---

## 6. PII Handling

**Rules:**
- Identify all PII at design time and document in the data model
- PII is not logged in plain text
- PII sent to AI providers is minimized; use pseudonymization or redaction where possible
- PII in AI prompts is flagged as a high-risk pattern and requires explicit justification
- Data subject access and deletion requests must be supportable
- Consent management is documented where applicable
- PII fields in the database are identified in the schema documentation

---

## 7. Prompt Injection Defense

Applies to all projects that pass user-supplied text to an LLM.

**Rules:**
- Treat all user input as potentially adversarial
- User input is separated from system instructions through structured prompt templates
- Never interpolate raw user text directly into instructions: use parameterized slots
- System prompt content is not disclosed to users
- Prompt injection test cases are part of the security test suite
- AI output is validated and sanitized before being used in downstream operations or displayed
- Tool calls generated by AI require explicit allowlisting and authorization checks

**Defense layers:**
1. Input validation: reject inputs that match known injection patterns
2. Structural separation: system prompt and user content are clearly delimited
3. Output validation: AI output is parsed and validated before use
4. Tool authorization: AI-requested tool calls are checked against an allowlist
5. Logging: all prompt injection attempts are logged and alertable

---

## 8. Tool Authorization

Applies to all agentic projects (P02, P04, P07, P09).

**Rules:**
- Every tool the agent can call is defined in an explicit allowlist
- Tools with external side effects (write, delete, send, execute) require human confirmation by default
- Tool permissions are scoped: an agent operating on Project A cannot call tools for Project B
- Tool call arguments are validated before execution
- All tool calls are logged: tool name, arguments (sanitized), result, and identity
- Budget limits apply to tool-calling loops: maximum tool calls per session, maximum cost per session

---

## 9. Input Validation

**Rules:**
- All external input (HTTP requests, file uploads, webhook payloads, queue messages) is validated at the ingress boundary
- Use schema validation (Pydantic, Marshmallow, Zod, or equivalent) for all request bodies
- Reject inputs that exceed defined size limits before processing
- File uploads are validated for: MIME type, file extension, maximum size, and content (not just metadata)
- Reject or sanitize inputs containing null bytes, path traversal sequences, or known injection patterns
- Validation errors return 422 with field-level detail; never expose internal schema details

---

## 10. Output Validation

**Rules:**
- AI-generated structured outputs (JSON, code, API calls) are validated against a schema before use
- Never execute AI-generated code without human review
- AI output used in SQL queries, shell commands, file paths, or HTML is sanitized against injection
- Confidence scores or uncertainty signals are used where available
- Outputs that fail validation are logged with the raw AI response for debugging; the operation fails closed

---

## 11. Audit Logging

**Rules:**
- Audit log entries are immutable: once written, they cannot be modified or deleted
- Log all: authentication events (success and failure), authorization failures, data access for sensitive entities, configuration changes, admin actions, AI-triggered external side effects
- Each audit entry includes: `timestamp`, `event_type`, `actor_id`, `resource_type`, `resource_id`, `action`, `outcome`, `ip_address` (or equivalent), `request_id`
- Audit logs are stored separately from application logs and have a longer retention period
- Audit log access is restricted to admin roles

---

## 12. Rate Limiting

**Rules:**
- All public endpoints have rate limits applied
- Rate limits are defined per: IP address, API key, and user account
- Rate limit headers are returned in responses: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`
- Exceeding the rate limit returns 429
- Rate limits are configurable via environment variables; defaults are documented
- AI endpoints have additional token-budget rate limits to prevent cost runaway

---

## 13. Abuse Prevention

**Rules:**
- Request size limits are enforced at the HTTP layer
- Async job queues have per-user depth limits to prevent queue flooding
- AI workflows have maximum iteration/step counts to prevent runaway agents
- Cost budgets per request, per session, and per user are enforced at the provider adapter
- Unusual patterns (high volume, large payloads, repeated failures) trigger alerts
- Content moderation is applied where AI accepts free-form user content

---

## 14. Dependency Security

**Rules:**
- All dependencies are pinned to exact versions in requirements files
- Dependency vulnerability scanning runs on every CI build (`safety`, `pip-audit`, `snyk`, or equivalent)
- Known high/critical vulnerabilities block the CI pipeline
- Dependencies are reviewed before adding new ones; prefer well-maintained packages
- Transitive dependency updates are reviewed, not applied blindly
- License compatibility is checked for new dependencies

---

## 15. Security Gate Checklist

Before any release, complete and document:

```
[ ] Authentication implemented and tested
[ ] Authorization implemented and tested for all protected operations
[ ] RBAC roles defined and permission checks verified
[ ] Input validation in place for all external inputs
[ ] Output validation in place for all AI outputs
[ ] Prompt injection test cases executed
[ ] Tool authorization allowlist reviewed
[ ] Secret leakage scan passed (no secrets in code, logs, or config)
[ ] PII exposure assessed and documented
[ ] Dependency vulnerability scan passed
[ ] Rate limiting configured and tested
[ ] Audit logging functional and tested
[ ] Data retention and deletion policies implemented
[ ] Secure error handling — no stack traces or internal details exposed
[ ] TLS enforced for all external communication
[ ] Security findings documented and risks accepted by security owner
```

Store the completed checklist in `docs/security/` for each release.
